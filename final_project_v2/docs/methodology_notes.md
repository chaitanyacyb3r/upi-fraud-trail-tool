# Methodology Notes — UPI Fraud Money-Trail Reconstruction Tool

## Why We Did NOT Train a Machine Learning Model

### The Problem: 50 Labeled Examples From One Generator

This project's fraud data is generated by a single Python script
(`fraud_storylines.py`) producing 50 mule accounts across 34 fraud rings.
Training a supervised model (e.g., XGBoost, Random Forest) on 50 positive
examples from one generator does not teach the model "what real-world money
laundering looks like" -- it teaches it **the specific fingerprint of our
synthetic generator's randomness**.

### Why SHAP Was Dropped

SHAP (SHapley Additive exPlanations) explains why a model made a specific
decision. If the model itself is overfit to generator artifacts, SHAP
produces plausible-looking explanations for wrong reasons -- making the
problem worse, not better, by giving false confidence.

### What Would Be Needed

A supervised ML model would become appropriate with:
- 1,000+ independently sourced, labeled fraud cases
- Multiple fraud typologies (not all from one script)
- An independent test set (holdout data never seen during development)

This is stated as future work, not a limitation to apologize for.

## Feature Selection: What Survived and What Didn't

### The Process

1. **18 features** were computed for all 548 accounts (graph-structural,
   money-flow, temporal)
2. Each feature was tested **independently** using ablation testing (same
   methodology as Phase 4's Fan-In/Layering evaluation)
3. All threshold percentiles (5/10/15/20/25%) were reported -- no
   cherry-picking the best-looking threshold
4. Features that passed ablation were then **stress-tested with camouflage**:
   normal transactions were injected into mule accounts to simulate
   real-world mule behavior (where mules have legitimate activity mixed
   with fraud)

### Camouflage Testing (Two Rounds)

**Round 1** (10-25 transactions, random counterparties):
- `avg_dwell_time` collapsed: 85.4% recall -> 16.7%
- `clustering_coefficient` collapsed: 47.9% -> 18.8%
- `reciprocity` appeared stable: 95.8% -> 95.8%

**Round 2** (30-60 transactions, social-circle counterparties):
- `reciprocity` degraded: 95.8% -> 66.7% (Round 1 stability was an
  artifact of random one-off counterparties creating no repeat pairs
  to reciprocate with)
- `degree_imbalance` degraded: 70.8% -> 60.4%
- `out_degree` survived: 95.8% -> 93.8%
- `unique_receivers` survived: 95.8% -> 95.8%

### Final Feature Selection

Only `out_degree` and `unique_receivers` are used in the risk score.
Both measure the same structural property: mule accounts send money to
very few distinct recipients (1-2 cashout accounts), while normal accounts
interact with 20-40+ recipients.

`reciprocity` and `degree_imbalance` were **dropped** despite showing
real signal, because:
- Reciprocity's apparent strength was inflated by camouflage methodology
- Adding them (Tier 2) raised hard-negative false positives from 0% to 35%
  while only catching 2 additional mules (48 vs 46)

---

## Risk Score Weights

Both features receive equal weight (0.5 each). This is the honest default
when domain literature does not justify asymmetry. These weights were
**NOT chosen by inspecting which values separate known mules from normals**
in this dataset -- that would be overfitting by eyeball instead of by
gradient descent.

## Known Limitations

### No Holdout Set

All reported performance (ablation thresholds, camouflage tests, final
comparison) was computed on the same 548-account population. There is no
independent test set the thresholds were validated against. This is
consistent with how the entire project operates (no train/test split
anywhere, including the original heuristics), but it means:

**All reported metrics reflect the same dataset used to derive them.** A
genuine holdout or a second independently-generated dataset would be needed
to confirm generalization.

### Sample-Size Honesty

- "95.8% recall" is 46 out of 48 mule accounts
- "0% FP on hard negatives" is 0 out of 20 accounts
- "1.7% FP on normals" is 8 out of 480 accounts

These are small-count ratios. A couple of accounts swinging either way
meaningfully changes the percentages. All metrics should be read with
this sampling noise in mind.

### Synthetic Data Artifacts

Mule accounts in this dataset are generated with structural properties
that may not match real-world mules:
- Limited transaction history (no prior legitimate activity)
- Predictable timing patterns (5-180 minute hop delays)
- No cross-ring transactions

The camouflage tests partially address the first limitation, but the
others remain. Real-world validation on actual case data is the only
way to confirm these findings generalize.

### Reciprocity as a Fraud Signal

Reciprocity's near-zero mule score is partly guaranteed by construction:
`fraud_storylines.py` never generates a reverse edge (mule never pays a
victim back). This is realistic for most fraud typologies, but is stated
as "consistent with our fraud model's design, not independently verified
against reciprocal-fraud edge cases."

## Verified Performance (Tier 1 Enrichment)

| System | Recall | FP-Normal | FP-HardNeg | Precision | Raw Counts |
|--------|--------|-----------|------------|-----------|------------|
| Fan-In alone | 56.2% | 0.0% | 0.0% | 100% | 27/48 TP, 0 FP |
| + Tier 1 (out_degree, unique_receivers) | 95.8% | 1.7% | 0.0% | 85.2% | 46/48 TP, 8/480 FP |

Fan-In alone catches 27 of 48 mules with zero false positives. Adding two
independently-validated graph features (survived two rounds of camouflage
stress-testing) raises detection to 46/48 mules (95.8% recall) at 8/480
false positives on normal accounts (1.7%) and 0/20 on adversarial
hard-negative accounts (0%).

This is a legitimate, evidence-based improvement -- not a black box.
